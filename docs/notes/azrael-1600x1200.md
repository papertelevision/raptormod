## The mode is 0x120, and the ceilings were not where they looked

| suspected ceiling | what it actually was |
|---|---|
| VESA mode number | **0x120**, not the VBE-spec guess 0x11C. The standard list stops at 1280x1024, so 1600x1200 is a DOSBox extension and the number is DOSBox's own |
| LFB one-bank window | **lifts itself.** The shift was already derived (`while 64KB << n < W*H`), so it picked 15 and reported 2,048 KB, first bank boundary at row 1310 of 1200 |
| video memory | not a ceiling. The mode is offered at the DEFAULT vmemsize and at 2 MB (1,920,000 fits in 2 MB). `vmemsize = 4` is headroom only |
| `vesa_modes` | **must be `all`.** 0x120 is not in the trimmed `compatible` list. The conf comment said the opposite and was wrong |
| the real one | **stride 1024 baked into 21 sites of hand-written overlay asm** |

## Verify a VESA mode WITHOUT running the game

Two techniques, and the second is the one that settles it:

1. **Read DOSBox's own mode table out of the exe.** A `0x28`-stride array of
   `{uint32 mode, uint32 type, uint16 w, uint16 h, ...}`; type is a BIT FLAG, `0x20`
   = `M_LIN8` (1<<5). In Staging it starts at file `0x6728E0`. Anchor by searching
   for the width/height pair, then **subtract 8** to reach the struct base — the
   first decode attempt read from the width field and got nonsense.
   8-bit modes offered: `069 100 101 103 105 107 **120** 16E 17D=1280x960 207=1152x864`.
   The last two are 4:3 fallbacks if 1600x1200 is too slow.
2. **BIOS-query it with a 56-byte hand-assembled COM.** `INT 10h AX=4F01h` into a
   buffer, then `INT 21h` 3Ch/40h/3Eh to write the 2-byte return plus the 256-byte
   ModeInfoBlock to a file; run it under a throwaway conf with `mount c <dir>` and
   `exit`, then decode the file from PowerShell. No assembler needed — emit the
   bytes from PowerShell. For 0x120: **ModeAttributes 0x009B (bit 7 = LFB), 1600x1200x8,
   BytesPerScanLine 1600, WinSize 64 KB, PhysBasePtr 0xC0000000** — the same base as
   0x101/0x103/0x105, so no LFB patch changes.

   Layout trap: with `FNAME` at 0x130 the code must be **exactly 0x30 bytes** and the
   filename **7 chars + NUL**. An 8-char name silently shifts every offset.

## The overlay asm was the work: 21 sites, three shapes

`shl eax,10` (x1024) at 14 sites, `shl reg,8` (rows->dwords) at 3, `imul edx,edx,1024`
at 3, and `and reg,511` row masks at 4. All now go through four helpers in
Build-AztMod — `A-RowsBytes`, `A-RowsDwords`, `A-RandRow` and `$INJ_X_MASK` — so the
stride is named once. `A-ImulEdxImm` was added to Asm.ps1.

* **Not a power of two, so `shl` becomes `imul`** (+3 bytes a site; the overlay had
  19 KB spare). The alternative — padding the buffer to a 2048 stride to keep the
  shift — would have meant rewriting the flat `rep movsd` injection copy into a row
  loop, and that copy is on the path that has frozen the game twice. **Keep the blit,
  pay the bytes.**
* **`and reg,511` had to go, not just grow.** It reached row 511 of 576 (89%, close
  enough to look deliberate) but would be 55% of 928 — the bottom half of the visor
  would never glitch. Replaced with a multiply-high: `imul reg,reg,rows; shr reg,16`
  on the 0..65535 the site already holds. Uniform at any height, 9 bytes.
* **One `shl eax,8` is NOT a stride.** `0x7174`-ish, `shl eax,8; or eax,edx`, builds a
  two-byte ink pair. A blind regex over `shl.*8` would have corrupted it.
* Verify the result by **counting opcodes in AZTCODE.BIN**: 12/3/3 `imul reg,reg,1600`,
  1/2 `imul reg,reg,400`, row pickers x928 (2), x919 (blocks, -9), x889 (tear, -39),
  and **zero** leftover `C1 E0 0A` / `imul 1024` / `and edx,511`.

## Two more absolute-pixel asserts, the same old trap

`$GAUGE_W_MAX = 136` and `$GAUGE_W_EXTRA = 2` were pixels measured on the 1024 HUD3,
and rejected correct artwork at 1600 (detected recess 203). Both now
`floor(x * $HS / 1.6)`, which reproduces 136 and 2 exactly at 1024 — and both had to
MOVE into the DERIVED block, because they sat above `$HS`. See
[[azrael-resolution-asserts]] and [[azrael-powershell-null-ordering]].

`$SYSMENU_W/H` (330x272) and `cornerRadius` (26) were the same kind of literal; now
`Hi 206`/`Hi 170` and `26*$HS/1.6`.

## src\Build-Art.ps1 — the art chain is now one command

The 10-generator chain existed only as prose. `.\src\Build-Art.ps1 -ScreenW w -ScreenH h`
runs it in order with every size derived from (w, h, panelScale). **Validated by
reproducing the shipped 1024 manifest to the pixel** before being allowed to overwrite
anything — do that for any future layout change.

Three things it had to solve:

* **Each generator needs its OWN process.** They all `Add-Type` PcxTool/Quantize and
  Add-Type is process-wide, so in-process the chain dies at whichever runs second
  ("the type name 'LeTool.Pcx' already exists"). It writes a temp .ps1 per step and
  runs `powershell -File`.
* **The log box needs a second pass, structurally.** Build-AztMod sizes the frame from
  the scan-readout region it measures out of the *finished* panel art, so the number
  cannot exist until HudSkin has run. Flow: Build-Art -> Build-AztMod (throws, naming
  `-BoxW/-BoxHOff/-BoxHOn`) -> `Build-Art -Only HudBox -BoxW ...` -> Build-AztMod.
* **H1 is recess + GAUGE_W_EXTRA**, not the bare recess, so the HudBar step reads
  hud-layout.json *inside* the child process and adds the overhang.

`Build-HudBox` wants one page with BOTH frames on it; only separate `boxoff-4x.png` /
`boxon-4x.png` exist (`box-surround-4x.png` holds one panel on black and fails the
two-panel check). Build-Art composes `design\box-pair-sheet.png` from the pair on
first use.

## What 1600x1200 costs, and what is still undone

* **The viewport is 1600x928, not 1600x900.** 49 + 928 + 223 = 1200. The compass band
  is deliberately NOT scaled ([[azrael-hud-viewport-locked]], and the `$VIEW_Y` note),
  so the height falls out of the panel math rather than an aspect. 928 is 28 rows MORE
  than exact 16:9 would give.
* **The texture reserve is the tight part: 24 MB of a 29.9 MB block, leaving the cache
  ~6 MB.** It cannot be scaled by the 2.44x pixel ratio (that lands at 48 MB, past the
  whole block) because `memsize` is pinned at 32 by the extender. Err HIGH: a small
  cache only costs re-uploads, a small reserve is a fatal failed allocation. First
  thing to walk back if big rooms misbehave — see [[azrael-texture-cache-reserve]].
* **ALL 11 MOVIES ARE NOW UNDERSIZED.** Stock movies are 552-wide (viewport-sized) and
  the mod re-encoded every one at 1024 wide; at 1600 they draw into part of the surface
  only. ~660 MB of .MOV would have to be re-encoded to ~1.6 GB, which is hours — see
  [[azrael-loh-retention-trap]] and [[azrael-mov-format]]. Deliberately NOT done until
  the resolution is judged worth keeping.
  **2026-10-08: Josh will re-render the videos himself later.** A host-side full-screen
  player (decode the .MOV in the watcher, synced to word [0x162FE0]) was scoped and DROPPED
  at his request; don't re-propose it. Its findings: the player draws 1:1 at
  ((1600-w)/2,(1200-h)/2) via patched constants at 0x20CF5/0x20D14, and the overlay
  can't read the screen before 3D calibration, so the startup movies can't be stretched
  from the screen.
* Stills that DID have to be regenerated, because the engine blits them 1:1 into a
  screen-sized surface and the allocator never clears: TITLE, NEWLOGO, BACKDROP
  (Build-Credits, `-InDir C:\Games\azrael-gfx\credits`), HELP (Build-Screens) and the
  91 book pages. A short image leaves uninitialised heap around it.
